# Drive証憑から立替経費の仕訳候補を作る

経費申請の承認フローは設けません。人別・月別フォルダへの証憑格納を受付とし、
計上時に情報不足・重複・ルール不一致を確認する運用です。
本段階は読取専用のドライランであり、MF登録・CSV出力・Drive変更は行いません。

## フォルダ構成

```text
経費ルート/
  社員A/
    202609/          ← 対象月のPDF・JPEG・PNG
    202608_計上済/   ← 取込対象外
  社員B/
    202609/
```

- 人別フォルダのIDから社員ID・MFで使用する社員の取引先名・部門を明示的に対応付けます。
  名前やアップロード者から社員を推測しません。フォルダ名を変更してもIDは使い続けます。
- 月フォルダ名は `YYYYMM` と完全一致するものを1つだけ処理します。
- 対象月に `YYYYMM_計上済` があればその社員の同月全体を除外します。
  通常フォルダとの混在、同名月フォルダの重複は注意事項に残します。
- 月フォルダの不在・空、未対応形式、ショートカット、想定外の階層を注意事項に残します。
  サブフォルダやショートカットの先へは進みません。
- ルートの共有ドライブIDを取得し、共有ドライブと全ページの読取に対応します。
  権限エラー・不完全検索・不正レスポンス時は出力せず中止します。
- 月フォルダ名は対象期間であって証憑の利用日ではありません。利用日は証憑から別途確認します。

## APIキー不要のデモ

Node.js 22以上、依存関係導入済みの環境で実行します。

```bash
npm run typecheck
npm test
npm run accounting:demo
```

架空の5件から「候補1件・要確認3件・入力不正1件」を出力します。
デモ科目・部門・税区分・証憑ハッシュは本番用ではありません。
`examples/accounting/` に実データを置かないでください。

## Driveから一覧を取得する

1. `config/drive-expenses.example.json` を参考に、Git対象外の `.data/drive.json` を作ります。
   実際のルートフォルダID、組織ID、対象月、社員ごとの設定を記入します。
   社員情報が未確定なら `people: []` として一覧を取得し、後で設定できます。
2. 対象Driveを読める短期アクセストークンを `.env` の `GOOGLE_DRIVE_ACCESS_TOKEN` に設定します。
   メタデータ読取用の `drive.metadata.readonly` スコープで足ります。
   このCLIはトークン発行・更新を実装していません。期限切れ時は再取得が必要です。
   CodexのDrive接続は、このアプリの実行時認証に引き継がれません。
3. 次を実行します。

```bash
npm run accounting:scan-drive -- --config .data/drive.json --output .data/scan-202609.json
```

出力は正規化入力のひな形です。`records` にファイルID、フォルダ情報、社員設定、
証憑URL、Driveが提供する場合のSHA-256を保存し、`scanNotices` に注意事項を残します。
日付・金額・用途などのOCRはまだ行いません。ファイル内容もダウンロードしません。
フォルダ内に請求書や注文控えがある場合も、ファイル名だけで「本人が立替済み」とは判断せず、
後続の証憑確認で支払方法・二重計上の有無を確かめてください。

## 証憑データを検証する

スキャン結果の不足項目を証憑に基づいて補完します。未確定項目は省略し、推測で埋めないでください。
`transactionDate`（YYYY-MM-DD）、整数円の `amount`、`category`、`merchant`、
`description`、`department`、`employee.accountingCounterparty` と証憑SHA-256が必要です。
税区分や勘定科目は証憑と会社の会計方針に対応する正式なルールで決めます。

正式ルールは `config/accounting-rules.example.json` を参考に `.data/rules.json` に保存します。
借方・貸方の両方に税区分を設定してください。無効なルールは使用されず、
有効ルールに未設定の `__...__` がある場合はバッチ全体を拒否します。
社員ごとに部門が異なる場合は `departmentHint` を条件にしてルールを分けます。

```bash
npm run accounting:review -- --input .data/scan-202609.json --rules .data/rules.json --output .data/review-202609.json
```

- `candidate`: 入力と設定が揃い、仕訳候補を生成できた行。貸方取引先は支払先店舗ではなく精算する社員。
- `needs_review`: 不足、対象月外、社員の未設定、重複、ルール不一致などで候補を作らなかった行。
- `invalid`: 存在しない日付、不正金額、未知の項目など、入力形式が不正な行。

候補の `approvalStatus: needs_review` は既存の仕訳出力制御用の状態であり、
経費申請の承認を求めるものではありません。本段階は出力・登録をしないため、
適用ルールが確定している行も含めて自動的な `approved` への変更は行いません。
後続の本番化で「自動計上可能な条件」と「人が計上前に確認する条件」を分けます。

レポートには `scanNotices` も引き継ぎます。候補件数だけでなく、取り込まれなかった
フォルダ・ファイルの理由も確認してください。CLIの成功コードは処理完了を意味し、
全行が計上可能という意味ではありません。既存出力は上書きしないので、再実行時は別名を指定します。
出力ファイルは所有者のみ読書き可能（0600）で作成します。

## 二重計上対策の範囲と未実装

同一バッチ内の「同じファイルID＋明細ID」または「同じ証憑SHA-256」を検出し、
重複する全行を止めます。不正データ行と重複する正常行も止めます。
1ファイルを複数明細に分割するケースも証憑重複として確認対象になります。
SHAがない場合、ファイル名だけで同一証憑とは判定しません。

立替経費の冪等キーは組織・Google Drive・ファイルID・明細IDから生成します。
金額、日付、フォルダ名、証憑内容を修正してもキーは変わりません。
ただし、バッチ間の処理済み台帳、修正・取消処理、MF側との照合、
別ファイルへ再アップロードされた証憑の過去横断照合は未実装です。
`_計上済` の印だけでは二重計上防止を完結できないため、本番自動登録には台帳が必要です。

今後の順序は、PDF/画像の内容抽出 → 正式な社員・会計マスタ設定 →
過去証憑との照合テスト → 処理済み台帳 → 会計への出力・登録です。
メール受領PDFとMFクラウド請求書の実接続も別途実装します。

## データ保護

実フォルダID、社員情報、証憑、トークン、取込結果は公開GitHubへ載せません。
`.data/` と `.env` はGit対象外です。レビューを標準出力にすると証憑情報が表示されるので、
実データでは `--output` を使い、CIログなどに流さないでください。
本機能はDriveの名称・配置・共有設定を変更しません。

参考: [Drive files.list](https://developers.google.com/workspace/drive/api/reference/rest/v3/files/list)、
[Fileメタデータ](https://developers.google.com/workspace/drive/api/reference/rest/v3/files)。
